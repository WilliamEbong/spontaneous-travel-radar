# Build decisions

Decisions made during the unattended build (2026-11-09). Each says what was chosen, why, and how to undo it.
Items marked **check** are ones William should look at.

- **D-01** Python 3.12 via `uv venv --python 3.12` (the PC only has 3.14). Matches the Actions runtime. Undo: any 3.12+ venv works.
- **D-02** `radar/flights.py` uses `fast_flights.fetch_flights_html` and parses Google's payload itself (both the "best" and "other" lists). fast-flights 3.1.0's `get_flights` drops the "best" list, which held the cheapest fares in the smoke test (499 vs 583). Version pinned `==3.1.0`. Undo: switch back to `get_flights` if upstream fixes it.
- **D-03** `exclude_basic_economy=True` kept, as your hard constraint requires. The smoke test shows the carry-on flag alone already makes ULCC fares realistic (Flair +$43 per person per leg, priced by Google), and the no-basic flag is what doubles the cheapest YYC→YVR fare for two (245 → 499) by hiding Flair and WestJet UltraBasic. If you want ULCC fares with a bag counted, flip `EXCLUDE_BASIC` in `radar/flights.py` to `False`. **Decided 2026-11-09 (William): keep basic fares excluded.** The bands move instead (D-04).
- **D-04** Flight bands kept as seeded, although realistic fares in the smoke test sat 2 to 3 times above the "bad" line (YVR 483 per person round trip vs 190). **Decided 2026-11-09 (William): retune from the project's own data, not by allowing basic fares.** After two weeks of scans (target: the digest of 2026-11-23), set each city's amazing/good/average in `config/scoring.yaml` to about its p10/p25/p50 `price_pp` from `data/weekly-summary.json` (p25 added to the summary for this).
- **D-05** Work is pushed straight to `main` of the public repo, as the task asks (the repo is the deploy target for the Actions scan and Pages). Commits are per task.
- **D-06** Rotation parity uses `zlib.crc32(airport)`, not `hash()` (Python salts string hashes per process, so `hash()` would rotate randomly). About 730 queries per scan, under the 900-attempt budget.
- **D-07** `LegQuery` carries `origin_tz`/`dest_tz` so `fetch_leg` can build tz-aware `Leg`s without a global airport table. The fetch cache directory is per scan day (`data/cache/<date>/`); `--offline` points it at `tests/fixtures/offline/`.
- **D-08** Las Vegas uses the `mid` hotel group (bar 1050). Every window includes a Friday or Saturday night, which the design prices as mid for Vegas, so the plan's weekday flag would never fire. Undo: set `hotel_group: cheap` in `config/cities.yaml`.
- **D-09** Component formulas scale with `weights` in `config/scoring.yaml` (each component is a 0..1 fraction times its weight), so tuning weights works without code changes. With the seeded weights the numbers match the plan exactly. The price curve is piecewise linear through amazing 40, good 28, average 14, and 0 at average + (average - good).
- **D-10 (check)** Events score counts distinct Ticketmaster events at big venues (venue name contains stadium, arena, field, center, garden, dome and similar, as whole words) on the window's days. A raw count saturates: Chicago returns about 240 events for one weekend. Venue capacity is not in the API, so the name match is a heuristic with some false positives ("Blues Center"). `hotel_spike` = 6 or more such events. Undo or tune: `BIG_VENUE` in `radar/events.py`.
- **D-11** Weather: forecast when every day of the window is within 15 days, else monthly climate normals (precip probability = rain days / 30). Weather is fetched once per city per scan day.
- **D-12 (check)** History logs, per city-window, the cheapest trip for each airport pair plus the score winner (flag `winner`), not every in-window pair. Every pair would be about 90,000 rows a day (tens of MB in a public repo); this is about 400 rows (~100 KB) a day. The route percentile compares a price with those logged prices. Undo: log all trips in `radar/main.py`.
- **D-13** SerpApi quota month = the month the search is made (`check_hotels(today=)`), not the check-in month; the counter `data/serpapi_usage.json` is committed. One search was used on 2026-11-09 to record the Chicago fixture (counted). SerpApi errors are not retried (a retry spends quota); the check reports `skipped: error`.
- **D-14** A hit's lodging uses the cheapest option's all-in total when SerpApi gives one (pre-tax otherwise); the hotel *band* uses pre-tax as the design says. Re-scoring with real lodging changes only lodging and total (the 0-100 score has no lodging term), so `finalize_hit` swaps those two fields instead of recomputing components.
- **D-15** In dry-run every candidate that reaches the hotel check is written to `hits/dry-run/` with its gate results and `is_hit`, so the digest sees near-misses; the re-alert rule only looks at earlier files with `is_hit: true`.
- **D-16** `latest.json` has `best_by_city` (one row per city: its top-scoring window) and `windows` (every city-window winner). The weekly summary is rewritten on every scan, so the Monday digest always reads fresh data whatever time the scan finishes.
- **D-17** At most 3 candidates per scan get a SerpApi hotel check (highest score first); others are written with `skipped: cap`. Spreads the 60/month cap. Tune `MAX_HOTEL_CHECKS_PER_SCAN` in `radar/main.py`.
- **D-18** If 15 fetches in a row fail, the scan stops fetching (`health.blocked: true`) and scores what it has, rather than burning 900 attempts against a block.
- **D-19** A re-run on the same day replaces that day's history file instead of appending duplicates. The fetch cache stores slimmed itineraries (only the fields `to_leg` reads).
- **D-20** Scan cron is 10:17 UTC (03:17 MST / 04:17 MDT) so an ~80-minute scan finishes before the Monday 07:00 digest. A push touching `index.html` or `site/**` redeploys Pages without scanning; every deploy checks out the latest `main`.
- **D-21** Bot commits use `chore: data scan YYYY-MM-DD` (your conventional-commit types) instead of the plan's `data:` prefix.
- **D-22** Dashboard band pills: amazing green, good blue, average gray (a deliberate neutral, so it fails the palette validator's chroma check on purpose), bad red. Each pill always shows its text label, so colour never carries the meaning alone. The sparkline is a single 2px series with hover/focus tooltips; the same numbers are in the "Price history table".
- **D-23** Fresh-context review fixes (2026-11-09): same-day re-runs ignore their own hit file and their own history rows; the hotel check runs only when the score and re-alert gates already pass (`skipped: gated` otherwise), saving SerpApi quota; fetching stops after 110 min (`--deadline-min`) so a slow day still commits; caches are written atomically and a corrupt cache file counts as a miss; time spans go through UTC (DST-safe); API-supplied names cannot inject markdown links into briefs; the workflow always commits the SerpApi counter, Pages-only pushes use their own concurrency queue, and `PYTHONTZPATH=""` makes Python use the pip `tzdata` package.
